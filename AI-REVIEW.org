#+title: AI-REVIEW --- points a human should check in AI-written code
#+author: Khalid Rafi
#+options: toc:2 num:nil

This file tracks the parts of AI-generated code in this channel that are worth
a human read: places where a plausible-looking change silently breaks at
run time rather than at build time.  Each entry says *what to look at*, *why it
is fragile* and *how to check it*; delete the entry once you are satisfied.

* TODO node-better-sqlite3: the hand-compiled native addon
=custom.scm=, package =node-better-sqlite3=, phase =compile-addon=.

Guix has no better-sqlite3, and upstream builds the addon with node-gyp driven
by npm's =install= script, which downloads node headers and prebuilt =.node=
binaries -- impossible in a sandbox.  So the phase compiles it with plain
=gcc=/=g++= instead: the SQLite amalgamation (=deps/sqlite3/sqlite3.c=, shipped
inside the npm tarball) plus the single C++ TU =src/better_sqlite3.cpp=, linked
into =build/Release/better_sqlite3.node=.

Review points:
1. *Compile defines* -- the =SQLITE_*/HAVE_*= list is transcribed from
   =deps/defines.gypi=.  If it drifts from what binding.gyp passes, the addon
   still builds and loads; it just behaves differently from upstream (missing
   FTS5, wrong =SQLITE_THREADSAFE=, ...).  Diff it against
   =deps/defines.gypi= after any version bump.
2. *C++ standard* -- =-std=c++20= must match =binding.gyp='s
   =cxx_std=.  A lower standard can compile and still give an ABI mismatch.
3. *Undefined symbols* -- the =.node= deliberately leaves node/v8 symbols
   undefined; the interpreter provides them at =dlopen=.  Hence
   =(delete 'validate-runpath)=.  Do not "fix" that by re-adding the phase.
4. *Version coupling* -- the addon is compiled against the headers of the =node=
   input.  Bumping node without rebuilding this package (i.e. reusing an old
   substitute) risks an ABI mismatch that only shows up at import time.
5. *NAPI flags (new in 13.x)* -- =napi-cflags= is transcribed from
   =binding.gyp='s =defines= and =cflags_cc= for the addon target; 12.x had no
   =defines= at all, so this list is version-specific rather than universal.  A
   wrong =NAPI_VERSION= or a dropped exception flag still compiles: the addon
   then marshals errors differently from upstream (=process.abort= on a thrown
   JS exception, or =undefined= where upstream would throw).  =-flto= is
   deliberately *not* copied over --- upstream's link step uses it, ours is the
   plain =g++= below, and a lone compile-time LTO flag only narrows the code.
   Re-read =binding.gyp= (not just =deps/defines.gypi=) on every major bump.

How to check: =./tests/smoke/mcode-bin.sh= loads the addon and runs the CLI; to
exercise the library itself:
#+begin_example
cd $(guix build -L . mcode-bin)/share/mcode-bin
node -e 'const D=require("better-sqlite3");const d=new D(":memory:");\
d.exec("CREATE TABLE t(a)");d.prepare("INSERT INTO t VALUES(?)").run(42);\
console.log(d.prepare("SELECT * FROM t").all())'
#+end_example

* TODO node-better-sqlite3: why =scripts.install= is neutralized, not deleted
Deleting the script is not enough: npm sees =binding.gyp= and runs
=node-gyp rebuild= itself, which fails for want of Python in the build
environment.  The phase therefore *replaces* the script with =true=.  If a
future version drops =binding.gyp= or npm changes that implicit build, this can
be simplified -- but test that =compile-addon= is still the only thing
producing the =.node=.

* TODO mcode-bin: node_modules symlinks instead of an npm install
=custom.scm=, package =mcode-bin=, phases =link-node-modules= and
=make-wrappers=.

The vendor npm bundle is installed as-is; its three native/runtime dependencies
are *symlinked* from the store into the app's own =node_modules=, so npm never
runs at build- or run-time.

Review points:
1. *Store layout coupling* -- each =symlink= hardcodes the dependency's path
   inside its output (=.../lib/node_modules/better-sqlite3=,
   =.../lib/node_modules/@vscode/ripgrep=, ...).  A Guix-side change to one of
   those packages leaves a dangling symlink that only fails when the CLI
   imports it.  The smoke test asserts =-e= (follows the link) plus a real
   =mcode --version=, so CI catches it.
2. *Wrappers, not shebangs* -- =cli.js= starts with =#!/usr/bin/env node=, which
   depends on the user's PATH; the =bin/mcode= wrapper execs node by store path
   instead.  Same reasoning as the other =*-bin= packages here.
3. *Why =mcode= (source) and =mcode-bin= coexist* -- =mcode= runs a real npm
   install offline and is what CI builds for correctness; =mcode-bin= is the
   cheap path that needs no npm at build time.  Keep both honest: a fix to the
   dependency wiring usually belongs in both.

* TODO check-static.sh: the style gate reformats on purpose, then compares
=tests/check-static.sh=, the =style_files= loop.

It used to be `guix style -f -n FILE | grep -q .`, on the assumption that =-n= is
a dry run.  It is not: with =-f=, guix style *rewrites* the file and prints
nothing, so the gate could never report a failure (CI's style step has been a
no-op) and every local "dry run" quietly reformatted the tree --- including the
generated =*-modules.scm= files, which the script deliberately skips because a
formatter and their generator should not fight.

Now it copies the file, formats for real, =cmp=s, and restores the copy either
way, so a *check* leaves no trace and a drift fails the job.  Review point: if
guix style ever fixes its =-n=, this can go back to the one-liner.

* TODO =*-bin= entry points collide with the source package /by design/

=zcode-bin= installs =bin/zcode=, which =zcode= also installs; =mcode-bin= does
the same against =mcode=.  An earlier revision renamed the =zcode-bin= CLI to
=zcode-cli= to make the collision go away.  That was wrong and it is reverted:
the .deb's own =bin= entry is =zcode= (upstream
=apps/zcode-cli/packages/cli/package.json=), and dodging the error would leave
two CLIs competing over one set of config, sessions and login state under
different names while neither wins.

Review point: if you ever see a =*-bin= shipping a suffixed binary name
(=foo-cli=, =foo-bin=, =foo-legacy=), treat it as a bug unless the *upstream*
tool is actually named that --- =bin/zcode-desktop= is legitimate only because
the deb's GUI binary is =zcode= and something else had to give, and the desktop
name is not what a user types.  Guix has no =conflicts= field on =package=, so
there is nothing to declare and the profile's default refusal is the only
guardrail.  See "Conflicts between a =*-bin= and its source package" in
README.org.

How to check: =GUIX_PACKAGE_PATH= guix install -p /tmp/t zcode zcode-bin= should
fail with a collision error, not silently pick one.

* TODO =zcode=: one upstream, two version variables

=%version= (3.14.3) labels the git tag the source build uses; =%bin-version=
(3.14.4) labels the vendor .deb on Z.ai's CDN.  They differ because the CDN is
ahead of the tag --- the desktop build ships before the repository is tagged ---
and a single variable would either break =%zcode-source='s hash or pin the .deb
to an artifact that no longer matches the label.

Review point: this only holds while the .deb really is built from a commit at or
near =%zcode-commit=.  On a bump, confirm both from
=./scripts/latest-version.sh= and do not "simplify" back to one variable.  A
silent divergence would look like a successful build of the wrong source.

* TODO =zcode=: the unpack silently depends on =bsdtar=, not =tar=

=custom.scm=/=zcode.scm=, =#:builder= manifest arm =("unpack" path …)=.

The npm tarball is extracted with libarchive's =bsdtar= and then
=chmod -R u+rwx=, not with GNU =tar=.  Some npm packages (=pngjs= is the one
that bit us) ship their /directories/ with mode 0666 --- no execute bit --- and
GNU =tar= aborts with "Permission denied" as soon as it tries to write a file
into such a directory.  =--no-same-permissions= does not help: umask can only
/clear/ bits, so it can never add the missing execute bit back.  =bsdtar= warns
about the bad modes and exits 0; the recursive =chmod= then restores what node
needs to descend the tree.

Review point: if anyone "simplifies" this back to =tar=, or drops the =chmod=
because "extraction already succeeded", the build breaks again --- and the
failure looks like a permissions bug in the sandbox, not a packaging choice.
Keep =(list "libarchive" libarchive)= in =native-inputs=; =bsdtar= is not on the
build PATH otherwise.

How to check: =./tests/smoke/zcode.sh=, or any =guix build zcode= from a clean
checkout (an already-populated store can mask it with a cached substitute).

* TODO =brow6el-bin=: =-Wl,-rpath-link= is load-bearing, and looks redundant

=custom.scm=, package =brow6el-bin=, phase =build-cef-wrapper=.

=libcef.so= ships =RUNPATH=$ORIGIN= and nothing else, and brow6el's
=CMakeLists.txt= sets =CMAKE_INSTALL_RPATH_USE_LINK_PATH FALSE=.  So although
glib, at-spi2-core, mesa, cups, expat, nspr/nss are all declared =inputs=, ld
has no search path for them when it resolves /libcef.so's own/ =DT_NEEDED=
entries --- and fails with ~600 "undefined reference" errors naming symbols
that plainly belong to packages in the graph.

The fix sets =LDFLAGS="-Wl,-rpath-link,<dir>"= for every input's =lib=, plus
=nss/lib/nss= (where Guix puts =libnss3.so=) and the copied =cef_binary/Release=.
Two things to note while reviewing:

1. It is /link-time only/ --- it does not touch the runtime rpath, which
   =install-cef-resources= sets with patchelf plus the =LD_LIBRARY_PATH= wrapper.
   Do not "consolidate" the two lists; they answer different questions.
2. The =-rpath-link= list is derived from =inputs= at run time, so adding a new
   library dependency needs no edit here.  That is also why it looks like magic:
   deleting an input from the package removes its dir from the search path, and
   the error you get back is an =ld= undefined reference, not a missing input.

Review point: if upstream brow6el ever stops using CMake's default link rule, or
starts setting =CMAKE_EXE_LINKER_FLAGS= itself, =LDFLAGS= would be ignored ---
CMake only reads it while /initialising/ the cache.  Symptom: the same wall of
undefined references returns despite correct inputs.

* TODO =zcode=: PATH order decides what =patch-shebang= writes into the store

=zcode.scm=, the =PATH= setup in the builder's let-bindings, and the
=(("bin" path target)= arm of =perform=.

Two facts about Guix meet in these two places, and together they make the PATH
order load-bearing:

1. The kernel resolves a =#!= interpreter /literally/; PATH is never consulted
   and =/usr/bin/env= does not exist on Guix.  So npm's own
   =#!/usr/bin/env node= shims die with "cannot execute: required file not
   found" (exit 127) unless something rewrites them --- a symlink on PATH does
   not help.  Hence =(patch-shebang prog)= in the =bin= arm.
2. =patch-shebang= writes back whatever =(search-path path cmd)= returns
   /verbatim/; it does not =canonicalize-path= (see =guix/build/utils.scm=,
   the =(bin (search-path path cmd))= line).  So if our =shim/bin= dir were
   first on PATH, the installed tree would carry a
   =#!/tmp/guix-build-zcode-.../shim/bin/node= shebang --- a path that stops
   existing the moment the build ends.  Hence =(dirname node)= goes /before/
   the shim dir.

Review point: moving the shim dir to the front of PATH looks harmless and is
not --- the builds still pass, and the breakage only shows up on the user's
machine, as an installed binary that says "cannot execute".  The same trap
applies to the chmod in that arm: it is applied to the /resolved/ program, not
to the symlink, because Guile's =chmod= follows links and would otherwise fail
on a broken =.bin= entry with an unhelpful error.

The first attempt at this was the /wrong shape/ and cost one CI run: patching
only the programs the =%zcode-node-bin-links= manifest names.  That list is not
complete.  pnpm creates =node_modules/.bin/tsc= itself, while the build scripts
run, out of a workspace =package.json= --- so no bin row ever names it, and the
build died on =tsc= with exactly the error the patch was supposed to prevent
(CI run 37179344851).  The fix is now a sweep of every shebang in the finished
tree, run after the manifest, with two details worth keeping:
- =lstat=, not =stat=.  pnpm's =node_modules/.pnpm/node_modules= links point
  back up at their own directory; following them loops forever.
- =find-files= with =#:directories? #t= does /not/ descend into symlinked
  directories, so it returns =node_modules/.bin= but none of its entries ---
  and those entries are precisely what bash =exec=s.  The =loop= re-enters each
  real subdirectory itself for that reason.

Review point: if the manifest ever needs to name a program /explicitly/ again,
it is no longer a correctness requirement, only a size optimisation.  Prefer
leaving it alone rather than adding rows that the sweep already covers.

* TODO =cline-baseline=: the fix that is only a guess

=sane-packages/cline.scm=, the =LD_LIBRARY_PATH= setenv in
=cline-baseline-build=.

CI run 37179344851 got as far as =bun install= (so the =#:modules= fix worked)
and then failed with =install script from "grpc-tools" exited with 127= and
=exec: cannot open shared object file=.  grpc-tools' install script is
=node-pre-gyp install=, which downloads a glibc-linked =protoc= and runs it;
that binary's =PT_INTERP= is the absolute path =/lib64/ld-linux-x86-64.so.2=,
which does not exist on Guix.

Review point: bun printed the message but not the /name/ of the missing
library, so pointing =LD_LIBRARY_PATH= at gcc's =lib= (which pulls in glibc)
is a well-reasoned guess rather than a diagnosis, and it is the one change in
this batch that is not confirmed by evidence.  If the next run fails the same
way, read the actual =protoc= ELF instead of adding another library:
=readelf -l= for =PT_INTERP= and =readelf -d= for =NEEDED=.  A missing
=libstdc++.so.6= is the likeliest alternative, which would mean also binding
=glib=; that possibility is why the note names gcc rather than glibc even
though the loader is what is missing.

* TODO =mcode=: =validate-runpath= is deleted, and there is no off switch

=custom.scm=, package =mcode=, =#:phases=.

The app ships vendor prebuilds (=better-sqlite3='s
=prebuilds/linuxmusl-x64.node= and friends) that name =libstdc++.so.6= and
=libc.musl-x86_64.so.1= by SONAME with /no RUNPATH at all/.  That is
deliberate on upstream's side: node =dlopen()s them and resolves them itself.
Guix's =validate-runpath= cannot succeed on such a file, and there is nothing
to fix in the binary, so the phase is deleted.

Review point: there is no gentler version of this.  =node-build-system= does
not accept =#:validate-runpath?= at all --- it is not among the arguments it
takes, and passing one aborts /evaluation/ with "Unrecognized keyword", which
reads like a typo rather than a rejected design.  So if you are ever tempted to
reintroduce the keyword, check that signature first.

* TODO =cline-baseline=: the source hash is still a placeholder

=sane-packages/cline.scm=, =%cline-baseline-source=.

=(sha256 (base32 "00000000000000000000000000000000000000000000000000"))= is
deliberate, not an oversight.  =cline-baseline-build= is a custom origin
method, and a derivation made that way is one of the few allowed to reach the
network, so CI can download the sources once and report the real hash.

Review point: the first CI run after this will fail /after/ doing the whole
Bun build, and the failure message contains the hash to paste back.  Do not
treat that failure as a regression, and do not substitute a hash for a
different file to make it go away.  Until the real hash lands, this package is
known-not-to-build and everything else in the channel is unaffected.

* TODO Vendor URLs must be versioned, not =latest=

=qoder-desktop-bin= was pinned at =(version "0.3.4")= while its URI ended in
=/latest/Qoder-linux-amd64.deb=.  The sha256 still matched, because the hash had
been taken from whatever the CDN served that day --- 0.4.3's bytes.  Nothing in
Guix can catch that: the derivation builds, the store path is correct, and only
the label lies.  Fixed by putting =version= into the path
(=/qoder-app/releases/VERSION/Qoder-linux-amd64.deb=).

Review point: for every =*-bin=, grep its URI for =latest=, =stable=, =beta= or a
bare =/download=.  Any of them plus a pinned sha256 is a version label with no
relationship to the artifact.  Prefer a path that contains =version=; if
upstream publishes no such path, say so in a comment next to the hash.

* How this file is used
Add an entry whenever AI-written code encodes an assumption that a compiler or
a test suite cannot check (transcribed constants, upstream layouts, implicit
tool behaviour).  Entries should be short enough to actually get read.
